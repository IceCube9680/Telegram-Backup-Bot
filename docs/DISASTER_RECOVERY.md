# Disaster Recovery & Backup Runbook

This document defines the Disaster Recovery (DR) model, backup automation strategies, recovery objectives (RPO/RTO), and step-by-step restoration procedures for the Telegram Backup Bot system.

---

## 1. Disaster Recovery Model & Objectives

| Objective | Target | Notes |
| :--- | :--- | :--- |
| **RPO (Recovery Point Objective)** | $\le$ 24 Hours | Determined by daily database and filesystem backup schedule. |
| **RTO (Recovery Time Objective)** | $\le$ 30 Minutes | Time required to provision clean containers, restore DB archive, extract storage, and run reconciliation. |
| **Data Scope** | Database Metadata + Physical Storage | MongoDB stores users, tasks, metadata, folders, tags; LocalStorage stores the binary backups. Both must be restored together. |

---

## 2. Backup Sources & Formats

1. **MongoDB Database Backup**:
   - Location: `backups/mongodb/mongo_backup_<TIMESTAMP>.archive.gz`
   - Generated by: `scripts/backup_mongodb.sh`
   - Format: Single compressed gzip archive using `mongodump --archive --gzip`.
   - Contains: All collections (`users`, `backup_items`, `backup_tasks`, `folders`, `tags`, `item_tags`, `user_settings`, `storage_usage`, `web_sessions`, `login_tokens`).

2. **Physical Storage Filesystem Backup**:
   - Location: `backups/storage/storage_backup_<TIMESTAMP>.tar.gz`
   - Generated by: `scripts/backup_storage.sh`
   - Format: Compressed tarball (`tar -czf`) preserving directory paths under `users/{user_id}/`.
   - Excludes: Temporary in-flight download directory `.tmp-downloads`.

## 3. Scheduled Backup Automation (Cron Example)

Add the following cron jobs to the host system via `crontab -e`:

```bash
# 1. Daily MongoDB Backup at 02:00 UTC (Retain 7 days)
0 2 * * * cd /home/icecube/ASUS/Telegram-backup-bot && ./scripts/backup_mongodb.sh >> /var/log/backup_mongo.log 2>&1

# 2. Daily Physical Storage Backup at 02:30 UTC (Retain 7 days)
30 2 * * * cd /home/icecube/ASUS/Telegram-backup-bot && ./scripts/backup_storage.sh >> /var/log/backup_storage.log 2>&1

# 3. Hourly Stale Temp Downloads Cleanup
0 * * * * cd /home/icecube/ASUS/Telegram-backup-bot && .venv/bin/python -m app.scripts.cleanup_temp --max-age-hours 1 >> /var/log/cleanup_temp.log 2>&1
```

## 4. Step-by-Step Restoration Procedure

In the event of total server loss, database corruption, or storage failure, follow this exact restoration sequence:

### Step 1: Deploy Clean Environment
Clone the repository and prepare `.env` configuration:
```bash
git clone https://github.com/example/Telegram-backup-bot.git /opt/telegram-backup-bot
cd /opt/telegram-backup-bot
cp .env.example .env
# Fill in production secrets, BOT_TOKEN, and MONGODB_URI
```

### Step 2: Verify Backup Archive Integrity
Before applying restore, verify the backup archive integrity:
```bash
python -m app.scripts.verify_backup /path/to/mongo_backup_YYYYMMDD_HHMMSS.archive.gz
```

### Step 3: Start MongoDB Service
Start only MongoDB to accept incoming restore:
```bash
docker compose -f docker-compose.prod.yml up -d mongodb
# Wait for healthcheck to pass
docker compose -f docker-compose.prod.yml ps mongodb
```

### Step 4: Restore MongoDB Data
Execute the database restore script:
```bash
./scripts/restore_mongodb.sh /path/to/mongo_backup_YYYYMMDD_HHMMSS.archive.gz --confirm
```

### Step 5: Restore Physical Storage Files
Extract the storage archive into the configured storage directory:
```bash
mkdir -p ./storage
tar -xzf /path/to/storage_backup_YYYYMMDD_HHMMSS.tar.gz -C ./storage
```

### Step 6: Start Full Application Stack
Start API, Bot, and Background Worker:
```bash
docker compose -f docker-compose.prod.yml up -d
```

### Step 7: Run Storage Reconciliation & Integrity Verification
Execute administrative verification to identify any drifts:
```bash
# 1. Audit referential integrity across collections
docker compose -f docker-compose.prod.yml exec api python -m app.scripts.integrity_check

# 2. Reconcile MongoDB records with physical files on disk
docker compose -f docker-compose.prod.yml exec api python -m app.scripts.reconcile_storage --repair

# 3. Verify overall health
docker compose -f docker-compose.prod.yml exec api python -m app.scripts.healthcheck
```

### Step 8: Post-Restore Verification Checklist
- [ ] MongoDB connection healthy.
- [ ] `/health/live` returns HTTP 200.
- [ ] `/health/ready` returns HTTP 200.
- [ ] Web dashboard opens and authenticates.
- [ ] Sample backed-up file can be downloaded and matches SHA-256.
- [ ] Send new test file to Telegram bot; worker downloads and processes it.
